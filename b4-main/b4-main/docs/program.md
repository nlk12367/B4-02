# 目前暫定企劃書
## 專案名稱
文件理解與結構化知識編譯系統（暫定）

---

## 一、企劃目的

本企劃的目的，不是再做一個單純的 OCR 工具，也不是再做一個只能把文件丟進去聊天的知識庫，而是要建立一套能將複雜文件轉換成「AI 更容易理解、檢索、驗證與使用」的中間資料層。

目前市場上大多數工具，通常只解決其中一段問題：
- 有些工具能把文字掃出來
- 有些工具能做結構化解析
- 有些工具能做向量檢索
- 有些工具能做工作流串接

但很少有工具，能把這些能力整合成一條對一般使用者也足夠友善、同時又能保留驗證、重試、追溯與資料品質控制的完整流程。

因此，本專案目前的核心方向，是把「文件處理」升級成「知識編譯」。

---

## 二、目前問題定義

在 AI Agent、RAG、知識庫建置的場景中，真正的問題通常不是資料不夠，也不是 Prompt 不夠長，而是：

1. 原始文件內容太亂
2. 文件格式差異太大
3. 長文直接輸入模型會造成注意力分散
4. OCR 結果雖然能抽字，但不理解版面與結構
5. 結構化模型雖然能理解內容，但成本較高，也可能產生不穩定輸出
6. 即使文件被成功解析，後續也未必能轉成適合下游 AI 使用的穩定資料格式

因此，本專案要解決的，不只是「讀文件」，而是：

- 怎麼選擇正確的解析方式
- 怎麼把結果整理成統一格式
- 怎麼進一步產生適合 AI 使用的分層知識資料
- 怎麼驗證這些資料是否可靠
- 怎麼證明這種方法比傳統全文 chunking 更有效

---

## 三、目前已有基礎

目前系統已具備以下基礎能力：

### 1. 雙路解析能力
- 標準 OCR 路線
- GPT 視覺結構化解析路線

### 2. 統一中間層
已具備將不同解析結果轉成統一乾淨文字表示的能力，可作為後續知識整理的基礎。

### 3. Checkpoint 與容錯
已具備任務狀態管理、重試與向量/資料暫存能力。

### 4. 多儲存派送
已具備將結果派送到不同儲存目標的能力。

這代表專案目前已經不是從零開始，而是已經完成了「文件進來 → 被讀出來 → 被送出去」的基礎流程。

---

## 四、目前最該收斂的方向

現階段最重要的，不是增加更多模型，也不是急著擴更多資料庫後端，而是先完成以下四件事：

### 1. 建立文件路由規則
需要先定義：
- 什麼文件適合走 OCR
- 什麼文件適合走結構化視覺解析
- 什麼文件需要雙路並跑後整合

這件事的目的是降低成本、提高穩定性，避免所有文件都走同一種高成本流程。

### 2. 統一輸出 JSON Schema
不管走哪一條路線，最後都要輸出成統一格式。

建議至少包含：
- document_id
- route_used
- document_type
- raw_text
- sections
- tables
- key_facts
- source_pages
- confidence
- needs_review

這樣後面才能真正比較不同路線的輸出品質。

### 3. 建立 L1 / L2 / L3 分層知識表示
這是目前最值得做的差異化核心。

#### L1：摘要層
用途：讓下游 Agent 快速理解這份文件在做什麼。

#### L2：事實層
用途：做主要檢索與問答，作為向量化主體。

#### L3：證據層
用途：保留原始段落或證據內容，作為引用與回查依據。

這一步的目的不是多做一層格式，而是讓資料不再只是全文 chunk，而是變成不同用途的知識單元。

### 4. 建立驗證與評估機制
這是目前最關鍵的一步。

需要建立一套方式，判斷：
- 哪一條路的解析結果比較好
- L1 / L2 / L3 是否比原始 chunk 更適合下游 AI
- AI 回答的內容是否真的有根據資料
- 是否能減少 hallucination 與長文污染

## 五、目前最小可行版本（MVP 1）

### MVP 1 的目標
不是做完整商業化產品，而是先證明：

> 將文件解析結果整理成分層知識表示（L1/L2/L3），能比傳統原始全文切塊更適合下游 AI 問答與檢索。

### MVP 1 的流程
1. 上傳文件
2. 選擇或判斷解析路線
3. 產出統一 JSON
4. 從 JSON 生成 L1 / L2 / L3
5. 儲存於一般資料庫
6. 選擇性將 L2 / L3 向量化
7. 建立測試問答集
8. 比較不同資料表示方式的效果

### MVP 1 暫時不優先處理的事項
- 不急著支援所有檔案格式
- 不急著接更多向量資料庫
- 不急著自訓練大型模型
- 不急著擴成超大工作流平台

MVP 1 的重點是：先證明方法有效。

## 六、目前應該立刻做的事情

### 第一階段：規格定義
1. 定義文件分類條件
2. 定義統一 JSON schema
3. 定義 L1 / L2 / L3 格式
4. 定義 validation 欄位
5. 定義 confidence / needs_review 規則

### 第二階段：系統補齊
1. 將現有兩條解析路線接到統一 schema
2. 建立 L1 / L2 / L3 生成器
3. 建立簡單驗證器
4. 建立來源追溯欄位
5. 將結果存進 SQLite / Firebase

### 第三階段：評估設計
1. 選 10 份文件
2. 每份文件人工建立 5~10 題問題
3. 為每題建立參考答案與對應來源段落
4. 跑兩種方法比較：
   - 傳統 chunk 方法
   - L1 / L2 / L3 方法
5. 比較：
   - retrieval 命中率
   - answer correctness
   - groundedness
   - token 使用量
   - hallucination 情況

---

## 七、評估方法

目前最實用的評估方式，不是追求一個完美分數，而是建立可比較的測試流程。

### 評估面向一：檢索是否找對資料
問題提出後，系統抓回來的內容是否包含正確答案。

### 評估面向二：回答是否根據資料
回答是否來自 retrieved evidence，而不是模型自行補充。

### 評估面向三：回答是否正確
回答內容是否與人工參考答案一致。

### 評估面向四：回答是否真正解答問題
有些回答雖然沒錯，但沒有真正回答問題。

### 評估面向五：成本與穩定性
比較不同方法：
- token 成本
- 平均輸出長度
- 是否需要人工修正
- 結果是否穩定

## 八、目前差異化方向（暫定）

如果專案要走出和現有工具不同的位置，目前最值得主打的，不是「我也能解析文件」，而是：

### 1. 文件不是直接丟進模型，而是先被編譯成多層知識單元
### 2. 解析不是終點，還包含驗證、追溯與重試
### 3. 不同文件可以走不同解析路線
### 4. 輸出不是只有文字，而是可供 AI 與資料庫共同使用的中間資料層
### 5. 目標不是單純聊天，而是提升 AI 在長文件場景下的穩定度與正確率

---

## 九、目前暫定定位

本專案目前暫定的定位不是：

- OCR 工具
- 單純文件解析工具
- 單純 RAG 知識庫工具
- 單純 workflow 工具

而是：

> 一套將複雜文件編譯成 AI-ready、可驗證、可追溯、可分層知識資料的文件理解系統。

---

## 十一、結論

目前最重要的不是再擴功能，也不是急著訓練模型，而是：

1. 先把現有解析能力整合成統一輸出
2. 先把資料整理成多層知識表示
3. 先建立能驗證與比較的方法
4. 先證明這種方法對 AI 使用真的更好

只要這一步被做實，專案才有可能真正建立出和市場不同的位置，也才更有資格往研究、論文與產品化推進。
